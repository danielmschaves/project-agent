I/VII

In Brief

Five facts to anchor the rest

Project Agent is a git-versioned monorepo that treats the project record itself as the unit of work. The pipeline runs daily, ingests structured and unstructured sources, extracts events, surfaces signals, and opens a pull request. The human merges. That is the entire trust model.

Substrate
Markdown + NDJSON + DuckDB
Plain text on disk. Append-only event log. Materialized warehouse for queries.
Trust Gate
No PR, no action
Nothing externally observable happens without a human-merged PR. Cron-safe by construction.
Detection
Deterministic + LLM
Auditable SQL signals as the backbone. LLM signals as the radar. Both first-class.
Idempotence
Source-hash + cache
Two-layer: file hash dedup at ingest + LLM response cache at parse. Re-run produces zero diff.

The product is not the report. The product is the loop — the substrate, the pipeline that updates it, and the PR that gates every change. Reports are downstream artifacts; the same substrate generates them, drafts client emails, and (eventually) feeds specialized agents.

II/VII

The Inversion

What changes when the record is the work

Traditional project management is curation: a delivery manager assembles slides, spreadsheets, and meeting notes that describe what has already happened. Project Agent inverts that — the system maintains a continuously updated, machine-readable record, and the human's job becomes designing the signal layer that watches it.

Manual Era

The PM is a curator.

  • Slides assembled the night before the steerco.
  • Risks tracked in a shared spreadsheet that nobody opens.
  • Status reports describe last week, post-hoc.
  • Stakeholder context lives in one person's head.
  • The PM is a clerical bottleneck — the slowest input to the slowest report.
Signal-First Era

The PM is a delivery architect.

  • Records are versioned in git, machine-readable, continuously updated.
  • Risks surface as signals weeks before they hit a dashboard.
  • The status report is a derivation, not a deliverable.
  • Stakeholder context is queryable history.
  • The PM designs the schemas, audits the outputs, intervenes early.
"

The shift from describing what happened to surfacing what's about to is the whole product. Everything else is mechanism.

— Vision · PRD §0

The value proposition has three audiences nested inside each other. For the maintainer-of-one, it's a personal portfolio operating system — drop sources into an inbox, get a PR every morning with the diff that matters. For a small team, it's a substrate where any delivery manager can inherit any project by reading project.md. For the OSS release, it's a reference implementation of the signal-first pattern — opinionated about contracts, neutral about toolchain.

The MVP target is the first audience. The architecture is built so the third doesn't require a rewrite.

III/VII

The Architecture

Three load-bearing contracts, six pipeline layers

Three contracts carry the system. The first makes daily cron safe. The second makes a PM trust the output. The third makes Phase 5b possible without a rewrite. If any of them break, the rest of the design is decoration.

01

Idempotence

Anchored at two layers: source-hash dedup at ingest, LLM response cache at parse. The same source under the same prompt version produces byte-identical events. Re-run produces zero diff. Edited sources emit new events with supersedes links; the log stays append-only.

PRD §6.2 · Daily-cron safety
02

HITL Gate

The pipeline never takes externally observable action without a merged PR. No commits to main. No emails sent. No calendar events created. The human merge is what flips state. Everything else is a draft on a branch.

PRD §9 · Trust model
03

Package Boundary

All state mutation flows through src/project_agent/. Pipeline scripts and (Phase 5b) agents may not open the event log, the warehouse, or call the Anthropic SDK directly. CI lint enforces it from MVP onward. The substrate stays substrate.

PRD §5.1 · Multi-agent precondition

Above those contracts sits a six-stage pipeline. Each stage is one function. Each stage writes its summary to the operations log before returning.

Ingest
File-drop scanning. Hash each source, classify by type, register in manifest.
Deterministic
02
Parse
Cached LLM extraction. Rewrites project.md canonical sections. Emits events.
LLM + Cache
03
Warehouse Load
NDJSON → DuckDB views. Filters retracted and superseded events by default.
Deterministic
04
Analyze
Deterministic SQL + LLM detectors run over the warehouse. Every signal carries evidence event_ids.
SQL + LLM
05
Render
Composes project.md + project.notes.md + signals into a daily status report.
Template
06
Commit
Opens PR on auto/<date> branch with diff summary, signals, ops log. Human merges.
Git
Project record split
The project record lives across two files. project.md is bot-owned and fully rewritten by Parse on every run; the PM does not edit it. project.notes.md is PM-owned and never touched by the pipeline — free-form markdown for hypotheses, context, side conversations. Render composes both. This replaces the <!-- pm:* --> marker approach from v0.3, which would have lost work the first time a PM forgot the marker. Costs one extra file per project; removes the failure mode entirely.
Why these three contracts and not more
Other patterns matter — discriminated event payloads, the operations log, the anti-circularity rule for LLM signals — but they're consequences, not contracts. Get idempotence, HITL, and the package boundary right, and the rest follows. Get any of them wrong, and the rest cannot save you.

IV/VII

The MVP

Smallest valuable thing · Phase 0

MVP scope was trimmed deliberately in v0.4: file-drop ingest only, markdown reports only, three warehouse tables instead of five, twenty events instead of a hundred. The goal is to prove the shape of the loop. Backfill, HTML, and MCP all come in Phase 0.5 once the shape holds.

In Scope

Definition of Done

  • ✓
    One project onboarded with hand-curated project.md, empty/seeded project.notes.md, past artifacts in sources/_inbox/.
  • ✓
    python -m pipeline run --project <id> runs all six stages end-to-end with no manual intervention.
  • ✓
    Idempotence verified: a second run on the same day produces zero diff. Tested via clean git status + recording LLM client asserting no API call on cache-hit path.
  • ✓
    NDJSON contains ≥ 20 events spanning ≥ 7 days of project history.
  • ✓
    DuckDB warehouse exposes the tables MVP signals need: events, actions, blockers.
  • ✓
    Three deterministic signals fire on real data: action_aging, action_unowned, blocker_unowned. Each signal_detected event carries evidence event_ids.
  • ✓
    Markdown daily status report renders and commits via PR.
  • ✓
    Package-boundary lint passes (§5.1): no module under pipeline/ imports duckdb, opens NDJSON, calls Anthropic SDK, or edits project.md directly.
  • ✓
    project_agent.events.query exists as a first-class API. Without it, signals cannot be written and audit is theoretical.
  • ✓
    Operations log (data/runs/<run_id>.json) written per run, committed with the PR — per-stage counts, durations, errors.
  • ✓
    Event schema includes schema_version, run_id, source_hash, structured actor, confidence, supersedes/superseded_by, retracted/retracted_reason. payload is a discriminated union per event type.
  • ✓
    Test suite covers: schema validation, idempotence per stage, the boundary lint, the LLM-cache-hit path, and a smoke test asserting events.query returns deterministic results across two runs.

Sizing
1–2 weekends of focused build with Claude Code, per stage as a separate PR. Stage is "done" when: idempotence verified by clean git status + no boundary violations + operations log populated for both runs + events.query returns identical results. Don't merge ahead.
V/VII

Phased Development

From MVP to OSS release

Eight phases, each with explicit acceptance criteria in PRD §12. Phase boundaries are drawn where the cost of being wrong jumps — at the introduction of LLM signals, of portfolio scope, of external communication, of agent orchestration. Don't build ahead.

  • 00

    MVP — The Loop

    Current

    Prove the six-stage pipeline runs end-to-end and produces zero diff on re-run, on file-drop sources, with three deterministic signals.

    Deliverables One project onboarded · file-drop ingest · MD reports · events.ndjson + DuckDB warehouse with three tables · action_aging, action_unowned, blocker_unowned firing · ops log · package-boundary lint passing · idempotence + cache-hit tests. Acceptance DoD §10 verified end-to-end · idempotence across two consecutive runs · lint passing.
  • 0.5

    HTML + MCP

    Next

    Add design-system HTML rendering. Port the MCP ingest layer from the predecessor pipeline. Backfill 30 days of real history. Force the portfolio-PR-shape decision before a second project is added.

    Deliverables Jinja2 templates + CSS tokens · HTML status reports · project_agent.ingest.mcp ported · 30-day backfill on MVP project · portfolio-PR-shape decision documented. Acceptance HTML reports render with design system · MCP pulls real data without breaking idempotence · backfill complete · PR-shape decision recorded.
  • 01

    LLM Signals + Scheduled Operation

    Planned

    Activate LLM signals over the warehouse. Promote remaining deterministic signals as the warehouse tables that support them come online. Move to daily cron with a defined threat model for the host.

    Deliverables risk_escalation, risk_emergent, tone_shift (LLM) · risk_unaddressed, blocker_aging, deliverable_drift, stakeholder_inactivity (deterministic) · risks, decisions, milestones, stakeholders warehouse views · cron scheduling · cron-host threat model · per-project per-day LLM cost cap. Acceptance ≥ 1 LLM signal fires on real data · 5 consecutive cron days · cost cap enforced.
  • 02

    Portfolio Layer

    Planned

    Cross-project state. --all mode. Cross-project signals. Promote candidate signals that earned it during Phase 1.

    Deliverables python -m pipeline run --all · portfolio MD + HTML · cross-project signals (resource conflicts, stakeholder overload, correlated drift) · deliverable_dependency_stall (LLM) · candidate-signal review. Acceptance Portfolio HTML renders ≥ 3 projects with ≥ 1 cross-project signal.
  • 03

    Drafted Communications

    Planned

    The pipeline starts drafting outbound. Still no auto-send; everything stays HITL. Implement outbox storage policy before any client content lands in git.

    Deliverables Client status emails drafted in outbox/ (gitignored or routed to private store) · 1:1 prep notes from upcoming Calendar events · optional --send flag after PM approval · Slack/email PR notifications. Acceptance ≥ 1 outbox draft per week, PM-merged and sent · outbox storage policy implemented.
  • 04

    Backlog Integration

    Planned

    Native Jira replaces CSV export. Backlog signals come online — they were deferred from Phase 1 because they require this data. Round-trip writes from merged PRs back to Jira.

    Deliverables Native Jira read API · scope_churn and velocity_anomaly firing · round-trip Jira issue creation from PR-merged actions. Acceptance Jira read parity with CSV · one PR-to-Jira round-trip · backlog signals firing.
  • 5a

    PPTX Render

    Planned

    A new render target, not an architectural shift. Steerco deck generation via the Cowork skill.

    Acceptance Steerco PPTX generated for one project, reviewed, approved.
  • 5b

    Multi-Agent Substrate

    Planned

    Specialized sub-agents — Risk, Stakeholder, Scope — as thin wrappers over project_agent.* APIs. The package boundary makes this tractable, but does not solve orchestration on its own. That's the real work of this phase.

    Deliverables agents/ module populated · documented orchestration policy: conflict resolution, concurrency, cost budgeting · per-agent observability. Acceptance ≥ 1 sub-agent operating under §5.1 with documented orchestration.
  • 06

    Open Source Release

    OSS

    Strip personal config to .example files. Implement a PII / confidentiality boundary. Ship onboarding docs, demo project, license.

    Deliverables .example config files · PII redaction layer + internal_only event flag · synthetic project generator for tests · onboarding doc · demo project · screencast · MIT or Apache-2 license · contribution guide. Acceptance A second PM clones, onboards, and runs in < 1 hour · PII boundary tested.
VI/VII

Open Questions

Deferred on purpose · revisit at the named trigger

These were surfaced in the v0.4 review. Each is tagged with the phase that forces a decision and the trigger to revisit. Don't decide unilaterally; the cost of being wrong is higher than the cost of asking.

  • 01
    Phase 0.5 decision point

    Project-scoped or portfolio-scoped daily PRs?

    Per-project is simpler at one project. Portfolio-scoped (one PR per run, project subdirs, top-of-PR digest) scales better past two. The cost of being wrong is rework. Phase 0.5 forces this decision before any second project is onboarded. Recommendation: portfolio-scoped from day one — the digest is cheap, the rework isn't.

  • 02
    Phase 1 Security

    Where does the cron host live?

    Laptop (sleep = no run; tokens at rest on the dev machine), server (different threat model; needs hardening; tokens at rest), GitHub Actions (free-ish; tokens in CI secrets; slower auth refresh). Each is fine; none is automatic. Document in a one-paragraph threat model before scheduling.

  • 03
    Phase 3 Confidentiality

    Where do outbox drafts live?

    Drafted client emails in git history are a confidentiality risk that grows with the OSS release. Three options: outbox/ is gitignored and writes to a parallel private store; outbox/ lives in a sibling repo that isn't pushed; drafts are redacted to placeholders before commit. Decide before Phase 3.

  • 04
    Phase 0.5

    How big can a source artifact be?

    Large PDFs and email attachments will bloat the repo if naively committed. Options: Git LFS, external blob store, or gitignore raw binaries and rely on parsed-text representation. Decide before backfilling real history — backfill is when the bloat materializes.

  • 05
    Phase 1

    What happens when the LLM cost cap is hit?

    Per-project per-day budget. Three policies: fail the run, skip LLM signals and continue with deterministic only, or warn-and-continue. Different operators want different answers — make it configurable per project, default to skip-LLM with a pipeline_cost_high signal.

  • 06
    Phase 0.5

    How does OAuth refresh failure fail loudly?

    When tokens expire silently, the daily PR is empty. Easy to mistake for "nothing happened today" rather than "ingest is broken." The HITL invariant amplifies the silence. Need an ingest_failed event type and a pipeline_health signal so silent failure becomes loud failure in the PR description.

  • 07
    Phase 6

    Where does test data come from?

    MVP DoD wants ≥ 20 events. Real data → tests can't be public. Synthetic → need a generator. During MVP build, private fixtures from real history are fine. Before OSS release, build a synthetic project generator producing believable shape with no real PII.

  • 08
    Phase 6 Privacy

    Where is the PII / confidentiality boundary?

    Client data flows into events.ndjson and lives in git. No redaction story, no "render this risk internal-only." Single-user MVP defers this; OSS release cannot. Needs an internal_only payload flag honored by Render, and a redaction pass before any artifact leaves the local machine.

  • 09
    Phase 5b

    How do agents not collide?

    The §5.1 boundary is necessary for multi-agent but not sufficient. Real concerns left for Phase 5b: conflict resolution when two agents propose contradictory state, concurrency primitives for parallel events.append, per-agent observability, cost budgeting per agent loop. An agents/orchestrator.py design doc precedes any concrete agent — not the other way around.

  • —
    Closed in v0.4

    Are PM edits to project.md preserved via markers?

    No. The <!-- pm:* --> marker approach is gone. project.md is fully bot-owned and rewritten on every run; PM content lives in project.notes.md, which the pipeline never touches. Render composes both into the report.

VII/VII

Next Steps

The first week, in order

The shortest path from "design reviewed" to "MVP running on a real project." Each step is a separate concern; don't bundle. Each is gated by the prior. Resist the urge to build ahead.

  1. Scaffold the repo + package

    Day 0 · 1–2 hours

    Create the layout from PRD §5. src/project_agent/ as an installable Python package via pyproject.toml. Empty pipeline/, agents/, projects/, data/, prompts/, tests/. Commit the directory structure. The repo exists; nothing runs yet.

    → PRD §5 · CLAUDE §4.1

  2. Land the core contracts first

    Day 1 · half a day

    Three things, in one or two PRs: (a) Event pydantic model with the full v0.4 schema — schema_version, run_id, discriminated actor, discriminated payload, supersedes, retracted; (b) the events.append / events.query APIs in project_agent.events; (c) the package-boundary CI lint that fails the build. Idempotence and trust both ride on these.

    → PRD §6.2 · §5.1 · CLAUDE §1.1 · §4.2

  3. Onboard one project by hand

    Day 2 · 1–2 hours

    Pick a real or recent project. Hand-write project.md with the v0.4 front-matter + canonical sections. Seed project.notes.md with whatever ad-hoc notes you have. Drop 7+ days of sources (emails, meeting notes, docs) into sources/_inbox/. This is the test fixture for everything that follows.

    → PRD §6.1 · §10 (DoD #1)

  4. Build Ingest + Parse with the LLM cache

    Day 3–4 · the heaviest stage

    File-drop ingest with manifest + source-hash. The LLM cache wrapper around project_agent.llm.extract, keyed on (prompt_version, source_hash, model) — this is what makes idempotence work. prompts/extract-context.md with a version: 1 field. Parse rewrites project.md canonical sections and emits events. End-of-stage test: run twice, second run is a no-op with no Anthropic API call.

    → PRD §8.1 · §8.2 · CLAUDE §1.3

  5. Build Warehouse Load + Analyze with three signals

    Day 5 · half a day

    DuckDB views: events, actions, blockers. Filter retracted and superseded by default. The three MVP signals — action_aging, action_unowned, blocker_unowned — as SQL detectors that return event_ids on every row. Each signal_detected event carries evidence linking to source events. Verify the signals actually fire on the fixture data; if they don't, your fixtures are wrong.

    → PRD §8.3 · §8.4 · §7

  6. Build Render + Commit + ops log

    Day 6 · half a day

    Markdown status report templated from project.md + project.notes.md + this run's signals. data/runs/<run_id>.json populated by every stage. Git branch auto/<date> + PR with summary: new signals, status delta, ops-log link. The full loop runs.

    → PRD §8.5 · §8.6 · §6.4

  7. Run it twice, on the same day

    Day 6 · 30 minutes

    Second run. Assert: git status clean. Ops log shows zero new events. No Anthropic API call in the cache-hit path (use a recording client). The events.query API returns byte-identical results across both runs. If any of these fail, idempotence is broken — fix it before anything else.

    → PRD §10 (DoD #3) · CLAUDE §1.3

  8. Open the MVP merge PR, then stop

    Day 7 · review

    Self-review the PR as a whole. Verify every DoD item from PRD §10 is checked. Merge to main. Resist the urge to start Phase 0.5 immediately. Run the MVP on real data for a week. Note where you find yourself wanting a signal that doesn't exist — those are the candidate signals from PRD §7.1 earning their promotion.

    → PRD §10 · §15 · REVIEW_NOTES §3.9
After MVP
Phase 0.5 is the natural next move: HTML rendering and MCP ingest, both ported from the predecessor pipeline rather than built fresh. The portfolio-PR-shape decision is the only thing in 0.5 that requires real thought; everything else is mechanical. After 0.5, the system is operating on real data with cron, and the question shifts from "does the loop work" to "are the signals useful." That's where Phase 1 begins.
